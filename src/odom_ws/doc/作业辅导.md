## 1. 作业目标与数据流

本作业要使用**直接线性最小二乘法**，根据两种相对运动估计机器人里程计的校正矩阵：

- **里程计相对增量**：由 TF 中的 `odom -> base_link` 位姿计算；
- **激光相对增量**：由相邻两帧激光通过 PI-ICP / CSM 扫描匹配计算；
- **标定矩阵**：找一个 `3×3` 矩阵，将里程计增量映射到更接近激光匹配增量的结果。

源码的数据流如下：

```text
/sick_scan + TF(odom -> base_link)
        │
        ▼
cal_delta_distance() ──> odom_increment
        │
        ├──────────────> PIICPBetweenTwoFrames() ──> scan_increment
        │
        ▼
Add_Data(odom_increment, scan_increment)
        │
        ▼
Solve() ──> correct_matrix
        │
        ▼
correct_matrix × odom_increment ──> /calib_path_pub_
```

需要完成的函数：

| 文件 | 函数 | 任务 |
|---|---|---|
| `src/calib_odom/src/main.cpp` | `cal_delta_distance()` | 根据相邻两次里程计绝对位姿，计算局部坐标系下的相对增量。 |
| `src/calib_odom/src/Odom_Calib.cpp` | `Add_Data()` | 用一组里程计/激光增量构建最小二乘方程 `Ax=b`。 |
| `src/calib_odom/src/Odom_Calib.cpp` | `Solve()` | 解最小二乘方程，把 9 个未知数还原为 `3×3` 校正矩阵。 |

## 2. 第一步：完成 `cal_delta_distance()`

位置：`src/calib_odom/src/main.cpp` 中的 `cal_delta_distance()`。

### 2.1 输入和输出的含义

输入是当前时刻在全局 `odom` 坐标系下的绝对位姿：

```text
now_pos = [x₁, y₁, θ₁]ᵀ
```

函数内部已保存上一帧绝对位姿：

```text
last_pos = [x₀, y₀, θ₀]ᵀ
```

输出必须是“**当前帧在上一帧机器人坐标系下的相对运动**”：

```text
d_pos = [Δx_local, Δy_local, Δθ]ᵀ
```

### 2.2 不能只做全局坐标相减

下面这个做法不够：

```text
Δx = x₁ - x₀
Δy = y₁ - y₀
```

原因：这仍然是 `odom` 全局坐标系的位移；而后续 CSM 初值和标定模型使用的是机器人相对运动。

正确的推导步骤：

1. 先计算全局坐标系的位置差：

   ```text
   Δp_world = [x₁ - x₀, y₁ - y₀]ᵀ
   ```

2. 用上一帧的朝向 `θ₀`，把这个差值转换到上一帧车体坐标系：

   ```text
   Δp_local = R(θ₀)⁻¹ · Δp_world
   ```

3. 计算角度差：

   ```text
   Δθ = θ₁ - θ₀
   ```

4. 将 `Δθ` 归一化到 `[-π, π]`。

> 思考：二维旋转矩阵 `R(θ)` 将车体坐标转到世界坐标。既然现在要反向从世界坐标转回上一帧车体坐标，就应该使用什么矩阵？它和 `R(θ)` 的转置有什么关系？

### 2.3 手算自检用例

写完后，不运行 ROS，也应先手算这些例子。

#### 用例 A：朝 x 正方向前进

```text
last = [0, 0, 0]
now  = [1, 0, 0]
```

预期局部增量：

```text
[1, 0, 0]
```

#### 用例 B：朝 y 正方向前进

```text
last = [2, 1, π/2]
now  = [2, 2, π/2]
```

机器人朝向世界坐标 y 正方向，因此在自身局部坐标中是“前进 1 米”。预期：

```text
[1, 0, 0]
```

如果结果是 `[0, 1, 0]`，说明没有将世界坐标增量旋转回上一帧机器人坐标系。

#### 用例 C：跨越 ±π 的转向

```text
last_yaw = 179°
now_yaw  = -179°
```

实际转角接近 `+2°`，而不是 `-358°`。这正是角度归一化的必要性。

### 2.4 第一帧处理

第一帧没有前一帧，因此不能构成运动增量。当前代码已经通过 `has_previous_odom_pose_` 做了首帧保护：首帧只用来建立参考位姿并直接返回。

实现时需要保证：

- 参考位姿只在本次调用结束后更新；
- 返回前不会使用未初始化的 `d_pos`；
- 后续每帧都基于上一帧而非原点计算增量。

## 3. 第二步：推导 `Add_Data()` 的 `Ax=b`

位置：`src/calib_odom/src/Odom_Calib.cpp` 中的 `Add_Data()`。

### 3.1 从代码读出矩阵规模

在 `Set_data_len()` 中：

```cpp
A.conservativeResize(len * 3, 9);
b.conservativeResize(len * 3);
```

因此：

```text
A : 3N × 9
x : 9 × 1
b : 3N × 1
```

每一对输入增量提供 3 个标量方程；未知数是一个 `3×3` 校正矩阵的 9 个元素。

### 3.2 写出标定模型

调用处是：

```cpp
correct_inc = correct_matrix * odom_inc;
```

因此建模关系为：

```text
scan_increment ≈ correct_matrix × odom_increment
```

定义：

```text
odom = [ox, oy, oθ]ᵀ
scan = [sx, sy, sθ]ᵀ

M = [m00 m01 m02
     m10 m11 m12
     m20 m21 m22]
```

你需要先亲自在纸上把下式展开成三个标量方程：

```text
scan = M · odom
```

### 3.3 填矩阵前要回答的问题

对每组 `odom`、`scan`：

1. 第一条标量方程对应 `scan` 的哪个分量？
2. 第一条方程需要使用 `M` 的哪三个元素？其余六个未知数的系数是什么？
3. 第二、第三条方程如何对应 `M` 的第二、第三行？
4. 第 `k` 组样本的三行在 `A`、`b` 的哪三个行号？
5. `now_len` 应在填入样本前还是填入样本后递增？为什么？

建议先写出一个通用的块矩阵结构：

```text
A_k = [ ? ? ?  ? ? ?  ? ? ?
        ? ? ?  ? ? ?  ? ? ?
        ? ? ?  ? ? ?  ? ? ? ]

b_k = [ ?
        ?
        ? ]
```

把 `?` 全部换成 `ox`、`oy`、`oθ`、`0` 和对应的激光观测值。确认后再写 C++。

### 3.4 数据数量与数组边界

`is_full()` 的语义是收集到设定数量的数据后允许求解。实现 `Add_Data()` 时要确认：

- 写入的行索引不超过 `A.rows() - 1`；
- 相同的一组数据只写一次；
- 收集到足够数据后不要继续越界写入；
- 只有成功完成扫描匹配的样本才应成为一组观测。

## 4. 第三步：完成 `Solve()`

位置：`src/calib_odom/src/Odom_Calib.cpp` 中的 `Solve()`。

### 4.1 目标

求一个最小二乘解：

```text
min ||A x - b||²
```

得到长度为 9 的向量 `x`，再按照你在 `Add_Data()` 采用的未知数排列顺序还原为：

```text
correct_matrix : 3 × 3
```

### 4.2 数值方法选择

优先研究 Eigen 的 QR 分解接口，例如 Complete Orthogonal Decomposition 或 ColPivHouseholderQR。不要自行直接计算：

```text
(AᵀA)⁻¹Aᵀb
```

原因：显式求逆会降低数值稳定性，特别是观测数据接近共线、旋转不足或里程计增量尺度差别很大时。

### 4.3 写回矩阵时的检查

完成求解后必须核对：

1. `x` 中第 0～2 个元素是否对应 `correct_matrix` 的第一行？
2. 第 3～5 个元素是否对应第二行？
3. 第 6～8 个元素是否对应第三行？
4. 这个约定是否与 `Add_Data()` 中 `A` 的列顺序完全一致？
5. 数据不足、秩亏时，是否应拒绝求解或给出明确提示？

临时单位阵只用于防止未初始化内存被使用；完成作业后，应让正常路径返回真正求得的矩阵。

## 7. 调试检查表

### 编译成功但节点不输出数据

依次检查：

```bash
rostopic list
rostopic echo -n 1 /sick_scan
rosrun tf tf_echo odom base_link
```

需要确认：

- `rosbag play --clock bag/odom.bag` 正在运行；
- 有 `/sick_scan`；
- 在相同时间戳可以查询 `odom -> base_link` 的 TF；
- 节点订阅的是绝对话题 `/sick_scan`；
- 机器人累计运动超过源码中设定的最小阈值。

### RViz 没有显示窗口或无法连接显示器

在宿主机图形会话中先运行：

```bash
cd /home/zachary/workspace/ROS_NOETIC/docker
./x11_setup.sh
```

当前宿主机使用 Wayland/Xwayland，脚本会寻找有效的 X11 cookie 并写入 `/tmp/.docker.xauth`。

### 只有前两条路径，没有第三条路径

检查是否已发布标定触发消息：

```bash
rostopic pub /calib_flag std_msgs/Empty "{}"
```

再检查 `Solve()` 是否已实际构造校正矩阵，以及 `odom_increments` 是否已有可用于重放的增量。

### 校正路径更差或矩阵异常

优先从以下方面检查：

1. `cal_delta_distance()` 是否把世界坐标的位移正确转换到上一帧局部坐标；
2. `Δθ` 是否归一化；
3. `Add_Data()` 的列顺序与 `Solve()` 写回矩阵的顺序是否一致；
4. 每组样本的激光增量和里程计增量是否配对；
5. 样本是否覆盖前进、侧向变化和旋转，而不是只有单一方向直线运动；
6. 是否检查了扫描匹配是否有效。

## 8. 推荐的辅导节奏

1. 先完成 `cal_delta_distance()`；
2. 用本文第 2 节的三个手算用例自检；
3. 编译并使用 bag 查看 `odom_path` 和 `scan_path` 是否开始产生；
4. 再把你推导出的 `A_k`、`b_k` 三行发给助教/辅导者检查；
5. 自己完成 `Add_Data()`；
6. 选择 Eigen 的 QR 类求解器完成 `Solve()`；
7. 回放 bag，发布 `/calib_flag`，比较 `odom_path` 与 `calib_path`。

完成每一步后再进入下一步，定位问题会容易得多。
