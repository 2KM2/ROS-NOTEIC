# 二维坐标变换与旋转矩阵基础

> 面向本作业中的 `odom`、`base_link`、`yaw`、相对位姿与旋转矩阵。  
> 对应代码：`src/calib_odom/src/main.cpp` 中的 `getOdomPose()` 和 `cal_delta_distance()`。

---

## 1. 为什么需要坐标变换

同一段真实运动，在不同坐标系下写出来的数值可以不同。

例如机器人面向北方（世界坐标的 y 正方向）前进 1 米：

```text
从世界 / odom 坐标系看：向 y 正方向移动 1 米，即 [0, 1]ᵀ
从机器人自身坐标系看：向前移动 1 米，即 [1, 0]ᵀ
```

它们描述的是**同一段运动**，只是参考坐标系不同。

本作业要比较两种相对运动：

```text
轮式里程计得到的相对运动
激光扫描匹配得到的相对运动
```

若要把两者放入同一个最小二乘模型，它们必须以相同的坐标系表达。因此要将从 `odom` 得到的位移，转换到上一帧机器人局部坐标系。

---

## 2. 本作业中的两个坐标系

### 2.1 `odom`：里程计参考坐标系

`odom` 是机器人启动后，由轮编码器、轮速、IMU 或它们的融合结果不断积分得到的局部参考系。

```text
它通常连续、平滑；
但可能因为轮胎打滑、轮径误差、轮距误差等逐渐漂移；
它不等于绝对真实世界坐标。
```

本工程中，`getOdomPose()` 查询的是：

```text
odom -> base_link
```

得到的 `pose` 是：

```text
base_link 在 odom 坐标系中的绝对位姿 [x, y, yaw]ᵀ
```

### 2.2 `base_link`：机器人车体坐标系

`base_link` 固定在机器人底盘上，会随机器人一起平移和旋转。

ROS 中移动机器人的常用约定为：

```text
x：车头前方为正

y：车体左侧为正

z：车体上方为正

yaw：绕 z 轴逆时针为正
```

平面机器人只关注：

```text
[x, y, yaw]
```

其中 `yaw` 就是机器人车头相对于 `odom` x 轴的夹角。

## 3. 向量和“坐标表示”

先区分：

```text
真实几何对象：一段实际位移
坐标表示：这段位移在某个坐标系下写出的数字
```

例如“机器人从 A 到 B 的移动”是唯一的，但可以表示为：

```text
在 odom 中：  Δp_odom = [0, 1]ᵀ
在上一帧机器人坐标中：Δp_local = [1, 0]ᵀ
```

这里的两个列向量不同，却表示同一个真实位移。

---

## 4. 二维坐标轴的单位基向量

二维坐标系的两个基本方向是：

```text
eₓ = [1, 0]ᵀ
eᵧ = [0, 1]ᵀ
```

一个局部坐标中的位移：

```text
p_local = [x, y]ᵀ
```

可以理解为：

```text
p_local = x · eₓ + y · eᵧ
```

也就是：

```text
沿局部 x 轴走 x
+
沿局部 y 轴走 y
```

---

## 5. 从单位圆推导旋转矩阵

### 5.1 旋转后的局部 x 轴

初始 x 轴单位向量是：

```text
eₓ = [1, 0]ᵀ
```

它长度为 1，和 x 轴的夹角是 `0`。

若机器人局部坐标系相对于 `odom` **逆时针旋转** `θ`，旋转后的局部 x 轴长度仍为 1，方向角变成 `θ`。

由单位圆：

```text
x = cos θ
y = sin θ
```

所以旋转后的局部 x 轴用 `odom` 表示是：

```text
eₓ' = [cos θ, sin θ]ᵀ
```

它表示：机器人局部“向前 1 米”在 `odom` 中的方向。

### 5.2 旋转后的局部 y 轴

局部 y 轴永远比局部 x 轴逆时针多 `90°`，因此旋转后的 y 轴方向角为：

```text
θ + π/2
```

所以：

```text
eᵧ' = [cos(θ + π/2), sin(θ + π/2)]ᵀ
```

利用三角恒等式：

```text
cos(θ + π/2) = -sin θ
sin(θ + π/2) =  cos θ
```

得到：

```text
eᵧ' = [-sin θ, cos θ]ᵀ
```

它表示：机器人局部“向左 1 米”在 `odom` 中的方向。

---

## 6. 旋转矩阵为什么是这个形式

局部位移：

```text
p_local = [x, y]ᵀ
```

含义是：

```text
沿旋转后的局部 x 轴走 x
+
沿旋转后的局部 y 轴走 y
```

因此它在 `odom` 中的表示为：

```text
p_odom = x · eₓ' + y · eᵧ'
```

代入上一节得到的两个基向量：

```text
p_odom =
  x · [ cos θ ] + y · [ -sin θ ]
      [ sin θ ]       [  cos θ ]
```

将 `x`、`y` 写成矩阵乘法：

```text
p_odom =
[ cos θ  -sin θ ] [x]
[ sin θ   cos θ ] [y]
```

所以，从局部坐标旋转到 `odom` 坐标的标准二维旋转矩阵是：

```text
R(θ) =
[ cos θ  -sin θ ]
[ sin θ   cos θ ]
```

### 6.1 如何记忆矩阵的两列

矩阵每一列就是一个“旋转后的局部坐标轴”在目标坐标系中的表示：

```text
第一列 [ cos θ, sin θ]ᵀ：旋转后的局部 x 轴（前方）
第二列 [-sin θ, cos θ]ᵀ：旋转后的局部 y 轴（左方）
```

---

## 7. 旋转矩阵的两个方向

### 7.1 局部坐标 → `odom` 坐标

已知机器人局部位移：

```text
p_local
```

要写成 `odom` 坐标：

```text
p_odom = R(θ) · p_local
```

其中：

```text
R(θ) =
[ cos θ  -sin θ ]
[ sin θ   cos θ ]
```

### 7.2 `odom` 坐标 → 局部坐标

本作业的 `cal_delta_distance()` 需要做的是反方向：

```text
已知 Δp_odom
求    Δp_local
```

即：

```text
Δp_local = R(θ)⁻¹ · Δp_odom
```

二维旋转矩阵是正交矩阵，有重要性质：

```text
R(θ)⁻¹ = R(θ)ᵀ = R(-θ)
```

所以：

```text
R(-θ) =
[  cos θ   sin θ ]
[ -sin θ   cos θ ]
```

最终有：

```text
Δx_local =  cos θ · Δx_odom + sin θ · Δy_odom
Δy_local = -sin θ · Δx_odom + cos θ · Δy_odom
```

这就是 `cal_delta_distance()` 里位置分量的来源。

---

## 8. 为什么本题使用上一帧的 `θ₀`

本作业计算两帧绝对位姿：

```text
上一帧 P₀ = [x₀, y₀, θ₀]ᵀ
当前帧 P₁ = [x₁, y₁, θ₁]ᵀ
```

先在 `odom` 坐标系计算位置差：

```text
Δp_odom =
[x₁ - x₀,
 y₁ - y₀]ᵀ
```

我们要表达“当前帧相对于**上一帧**机器人”的运动，所以局部坐标系应当是上一帧的 `base_link`，自然要使用上一帧朝向：

```text
θ₀
```

完整关系为：

```text
Δp_local = R(-θ₀) · Δp_odom
```

如果误用了当前帧 `θ₁`，表达的会是“在当前帧车体坐标中看回去”的位移，含义就不同了。

## 9. 三个手算例子

### 9.1 例一：面向世界 x 正方向，向前走

```text
θ₀ = 0
Δp_odom = [1, 0]ᵀ
```

因为：

```text
R(0) = [1, 0; 0, 1]
```

所以：

```text
Δp_local = [1, 0]ᵀ
```

含义：前进 1 米。

### 9.2 例二：面向世界 y 正方向，向前走

```text
θ₀ = π/2
Δp_odom = [0, 1]ᵀ
```

此时：

```text
R(-π/2) =
[ 0  1 ]
[-1  0 ]
```

因此：

```text
Δp_local =
[ 0  1 ] [0] = [1]
[-1  0 ] [1]   [0]
```

结果：

```text
[1, 0]ᵀ
```

虽然全局 y 增加了 1，但从机器人视角，它仍然只是向前走了 1 米。

### 9.3 例三：面向世界 y 正方向，向右走

```text
θ₀ = π/2
Δp_odom = [1, 0]ᵀ
```

计算可得到：

```text
Δp_local = [0, -1]ᵀ
```

因为机器人面向北方时，世界 x 正方向是它的右侧；ROS 约定左为 y 正，因此右移为 y 负。

## 10. 角度增量与角度归一化

位置增量需要用旋转矩阵换坐标系；偏航角增量本身只需要相减：

```text
Δyaw = θ₁ - θ₀
```

但角度有周期性：

```text
π 与 -π 表示同一方向
```

例如：

```text
θ₀ = 179°
θ₁ = -179°
```

直接相减为：

```text
-179° - 179° = -358°
```

但真实旋转只接近 `+2°`。

常用归一化公式是：

```text
normalized_delta = atan2(sin(Δyaw), cos(Δyaw))
```

它会将结果限制到：

```text
[-π, π]
```

---

## 11. 齐次变换：把旋转和平移写在一起

如果不仅要转换位移，还要转换一个点或位姿，常使用 `3×3` 齐次变换矩阵：

```text
T(θ, tx, ty) =
[ cos θ  -sin θ   tx ]
[ sin θ   cos θ   ty ]
[   0        0      1 ]
```

二维点改写成齐次形式：

```text
p = [x, y, 1]ᵀ
```

则：

```text
p_odom = T · p_local
```

本作业的 `cal_delta_distance()` 只需处理两帧之间的**位移增量**，平移原点已经在做差时抵消，因此使用 `2×2` 旋转矩阵就足够。

## 12. 与作业代码的对应关系

`getOdomPose()` 从 TF 获取：

```text
base_link 在 odom 下的绝对位姿 [x, y, yaw]ᵀ
```

`cal_delta_distance()` 的工作流程是：

```text
1. 保存当前 absolute odom pose 为 now_pos
2. 计算 dx_world = x₁ - x₀、dy_world = y₁ - y₀
3. 读取上一帧朝向 theta_0
4. 使用 R(-theta_0) 将 [dx_world, dy_world]ᵀ 转为局部增量
5. 计算并归一化 yaw 增量
6. 将 now_pos 更新为下一帧使用的 last_pos
```

其返回值：

```text
d_pos = [forward, left, delta_yaw]ᵀ
```

之后会被用作：

```text
- CSM / PI-ICP 的初始运动估计；
- 与激光扫描匹配结果构造标定方程；
- 通过校正矩阵重新积分得到校正路径。
```

## 13. 常见错误检查表

### 错误一：直接返回 `now_pos - last_pos`

问题：前两个分量仍在 `odom` 坐标系，不是上一帧机器人局部坐标系。

### 错误二：旋转方向写反

本题是：

```text
odom → 上一帧局部坐标
```

因此应该用：

```text
R(-θ₀)
```

而不是 `R(θ₀)`。

### 错误三：使用当前帧的 `θ₁`

本题要求当前位姿“在上一时刻坐标系中的坐标”，因此应使用 `θ₀`。

### 错误四：更新 `last_pos` 太早

若在计算前写：

```text
last_pos = now_pos
```

则上一帧信息被覆盖，后续差值自然为零。

正确顺序是：

```text
先计算增量，再更新 last_pos。
```

### 错误五：没有归一化角度

跨越 `π`、`-π` 边界时，会出现接近 `2π` 的错误大转角。

### 错误六：混淆“全局位姿”和“相对增量”

```text
[x, y, yaw]：绝对位姿，表达在哪个坐标系中很关键；
[Δx, Δy, Δyaw]：相对运动，也必须注明在哪个坐标系表达。
```

## 15. ROS 导航与 `gmapping` 的常用 TF 坐标系

在 ROS 的二维移动机器人中，最常见的一条 TF 链是：

```text
map
 └── odom
      └── base_link（或 base_footprint）
           └── base_laser
```

从父坐标系到子坐标系的每一条边，表示“子坐标系在父坐标系中的位姿”。例如：

```text
odom -> base_link
```

表示机器人车体 `base_link` 在里程计坐标系 `odom` 中的位置和朝向。

### 15.1 四个坐标系各自表示什么

| 坐标系 | 原点通常在哪里 | 是否随机器人移动 | 主要用途 |
|---|---|---:|---|
| `map` | 地图定义的全局原点 | 否 | 全局建图、定位、全局路径规划、RViz 固定参考系 |
| `odom` | 机器人启动或里程计重置时的参考点 | 否 | 连续、平滑地描述机器人短期运动 |
| `base_link` | 机器人车体中心附近 | 是 | 表示机器人本体的位置、方向和运动 |
| `base_laser` | 激光雷达的测量参考点 | 是 | 表示激光雷达量测到的点 |

移动机器人遵循的常用轴向约定是：

```text
x：前方为正
y：左方为正
z：上方为正
yaw：绕 z 轴逆时针旋转为正
```

因此，`base_link` 中的 `[1, 0]ᵀ` 表示“向车头前方 1 m”，`[0, 1]ᵀ` 表示“向车体左侧 1 m”。

### 15.2 `base_link`、`base_footprint` 与 `base_laser`

`base_link` 是安装在机器人刚体上的本体坐标系，随底盘一起平移、转动。对于普通二维小车，原点往往放在两轮轴中心、底盘几何中心等便于建模的位置。

有些机器人还会使用 `base_footprint`：

```text
base_footprint -> base_link
```

它通常表示车体在地面平面上的投影，只保留平面运动；`base_link` 则可以保留真实车体的高度、俯仰和横滚。因此在平坦地面二维导航中两者可能重合或非常接近，但严格来说不是同一个概念。

`base_laser` 是雷达自身的坐标系。雷达相对底盘的安装位置和安装角一旦确定，关系通常不再变化：

```text
base_link -> base_laser
```

例如雷达位于车体中心前方 `0.20 m`、左侧 `0.05 m`，且正前方与车头一致，则该 TF 大致包含：

```text
平移：[0.20, 0.05, 安装高度]ᵀ
旋转：yaw = 0
```

这是一条**静态 TF**，一般由 URDF 或 `static_transform_publisher` 发布。激光消息中的点最初都以 `base_laser` 表达；ROS 通过 TF 才能把它们转换到 `odom` 或 `map` 中。

### 15.3 `odom`：连续、平滑，但会漂移

`odom` 来自轮编码器、IMU、视觉里程计或它们的融合。里程计节点通常发布：

```text
odom -> base_link
```

这表示“从启动到现在，里程计推算机器人走了多远、转了多少”。它很适合短时间的控制和局部规划，因为连续时刻之间通常平滑，不应突然跳变。

但轮胎打滑、轮径误差、轮距误差、编码器量化误差等会在积分中累积。例如真实运动距离为 `5.0 m`，里程计可能估计为 `5.2 m`。因此 `odom` 的特点是：

```text
短期相对运动：通常可靠且连续
长期全局位置：可能逐渐漂移
```

注意：`odom` 同时也是一个**坐标系名称**；而常被称为“odom topic”的 `/odom` 是一类 `nav_msgs/Odometry` 消息。两者有关联但不是同一个概念。典型情况下，里程计消息的位姿和 TF 中的 `odom -> base_link` 表达的是同一估计结果。

### 15.4 `map`：经地图匹配校正的全局参考系

`map` 用来表达机器人“在地图中”的位置，适合：

```text
全局地图显示
全局路径规划
基于已知地图的定位
SLAM 建图结果
```

在 RViz 中常将 `Fixed Frame` 设为 `map`，这样墙壁、栅格地图等全局对象保持稳定，机器人和激光数据则显示在地图中相应的位置。

不过，`map` 的原点是地图定义的原点，不保证必然与机器人启动时的 `odom` 原点重合。若系统选择让二者初始对齐，则刚启动时可以有：

```text
map -> odom = 身份变换
平移 = (0, 0)
yaw = 0
```

但这是常见初始化方式，不是所有系统都必须满足的规则。例如使用一张已有静态地图时，`map` 的原点由地图文件决定，机器人初始位姿则需要定位系统给出。

### 15.5 为什么需要 `map -> odom`

假设某时刻，里程计和激光匹配分别得到：

```text
odom -> base_link = (5.2 m, 0 m, 0°)
map  -> base_link = (5.0 m, 0 m, 0°)
```

前者是编码器积分结果，后者是地图/激光匹配后认为更可信的全局位置。为了使这两项同时成立，系统发布：

```text
map -> odom = (-0.2 m, 0 m, 0°)
```

于是按变换链组合：

```text
map -> base_link
= (map -> odom) × (odom -> base_link)
= (-0.2 m) + (5.2 m)
= 5.0 m
```

一般的二维刚体变换形式是：

```text
T_map_base = T_map_odom · T_odom_base
```

`map -> odom` 的作用正是把连续、但逐渐漂移的里程计轨迹对齐到全局地图。它承载的是**全局校正量**。

### 15.6 为什么不直接修正 `odom -> base_link`

SLAM 或定位系统可能在新一帧激光到来后发现过去的估计有误，例如需要修正 `30 cm`。若直接让 `odom -> base_link` 跳变 `30 cm`，依赖里程计连续性的局部代价地图、局部规划器和控制器可能会误以为机器人突然“瞬移”。

因此 ROS 的常用职责划分是：

```text
odom -> base_link：由里程计发布；尽量连续、平滑
map  -> odom：由定位或 SLAM 发布；允许为纠正全局误差而变化或跳变
```

这让局部控制可以使用平滑的 `odom`，而全局导航可以使用经校正的 `map`。

### 15.7 `gmapping` 与 `AMCL` 分别做什么

在典型配置中：

| 场景 | 节点 | 通常负责的 TF |
|---|---|---|
| 仅靠轮式/融合里程计运动 | 里程计节点、`robot_localization` 等 | `odom -> base_link` |
| 激光 SLAM 在线建图 | `gmapping` | `map -> odom`，并发布地图 |
| 已知地图中的激光定位 | `amcl` | `map -> odom` |
| 雷达安装外参 | URDF、静态 TF 发布器 | `base_link -> base_laser` |

因此，刚开始接触 `gmapping` 时，可以将其理解为：它用激光扫描与当前构建的地图进行匹配，发现并补偿里程计漂移，进而维护 `map -> odom`，同时生成 `map`。

完整的数据和变换路径可写为：

```text
轮编码器 / IMU
      ↓
发布 odom -> base_link

激光雷达
      ↓
base_laser 下的 LaserScan
      ↓（经 base_link -> base_laser 外参转换）
结合 odom 预测与激光匹配
      ↓
gmapping 发布 map -> odom，并生成地图
```

### 15.8 用一个激光点串起整条链

设雷达在自己的坐标系中检测到一个点：

```text
p_laser = [2, 0, 1]ᵀ
```

即雷达正前方 `2 m` 处有一个反射点。要将其显示到地图中，需要依次变换：

```text
p_map
= T_map_odom · T_odom_base_link · T_base_link_laser · p_laser
```

也可按坐标系路径记忆：

```text
base_laser -> base_link -> odom -> map
```

大量激光点完成同样的转换后，便能在 RViz 中落到地图对应的墙壁、障碍物位置上；`gmapping` 也正是依赖这种关系来建图与校正位姿。

### 15.9 常见误区

1. **`map` 和 `odom` 永远重合。**  
   不对。它们可能在初始化时对齐，但里程计漂移后，定位/SLAM 会通过 `map -> odom` 进行校正；已有地图场景下二者甚至一开始就未必重合。

2. **`map -> odom` 不为零说明里程计程序写错。**  
   不对。真实传感器存在误差，非零校正量通常是正常现象。只有在里程计全程准确且初始坐标系已对齐时，这个变换才应为身份变换。

3. **`base_link -> base_laser` 与 `odom -> base_link` 一样会不断变化。**  
   不对。前者是刚体安装外参，通常静态；后者描述机器人运动，动态变化。

4. **TF 只有坐标名称，没有实际数学意义。**  
   不对。TF 的每条边都是平移和旋转组成的刚体变换；整条链就是多个齐次变换矩阵的连乘。
