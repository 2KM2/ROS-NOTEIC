# 一、Dijkstra：不知道终点在哪，也能走出最短路

## 1.1 先把问题说清楚

**输入**：一张图 `G = (V, E)`，每条边有个**非负**代价 `c(u,v)`；一个起点 `s`。
**输出**：从 `s` 到每个点的最短代价 `d(v)`，以及对应的路径。

栅格地图就是一张图，只是长得不像：

| 图的概念 | 栅格里是什么                                                                        |
| -------- | ----------------------------------------------------------------------------------- |
| 顶点 V   | 每个空闲格子。本包用一维下标`id = y * width + x` 编号（`GridMap2D::toId`）      |
| 边 E     | 相邻格子之间的连接。4 邻域每格最多 4 条边，8 邻域最多 8 条                          |
| 边代价 c | 直走`1`，斜走 `√2`（`kSqrt2`）。见 `astar.cpp` 里 `kDX/kDY` 方向表的注释 |
| 障碍     | 不是顶点，等于把它和所有边一起从图里删掉                                            |

所以"栅格路径规划"和"图上最短路"是同一个问题。想清楚这一点，
后面所有教科书上的图论结论就都能直接用了。

一个必须记住的细节：**斜走的代价是 √2 而不是 1**。
如果你把它写成 1，算法照样能跑、路径照样能通，只是不再是最短路 ——
而且肉眼完全看不出来。这就是 `astar_selfcheck` 存在的理由。

## 1.2 为什么 BFS 不够

广度优先搜索（BFS）用一个普通队列，一层一层往外扩。它求的是**步数最少**的路。

只有当所有边代价都相等时，"步数最少"才等于"总代价最小"。8 邻域下边代价有 `1` 和 `√2`
两种，两个目标就可能分道扬镳。

严格算一下什么时候会分道扬镳。设某条路走了 `s` 步直线、`d` 步斜线：

```
步数 = s + d          <- BFS 优化这个
代价 = s + √2·d       <- Dijkstra 优化这个
```

假设 BFS 找到的最少步数是 `k`，它选了一条 `(s₁, d₁)`，`s₁ + d₁ = k`。
另有一条路 `(s₂, d₂)` 多走一步，`s₂ + d₂ = k + 1`。什么时候第二条**更短**？

```
s₂ + √2·d₂  <  s₁ + √2·d₁
```

令 `Δ = d₁ - d₂`（第一条多用了 Δ 个斜线）。由步数关系 `s₂ - s₁ = 1 + Δ`，代入化简：

```
1 + Δ < √2·Δ   =>   Δ·(√2 - 1) > 1   =>   Δ > 1/(√2-1) ≈ 2.414   =>   Δ ≥ 3
```

**结论**：只要存在一条路"多走 1 步、但少用 3 个斜线"，BFS 就会输。
比如 `3` 个斜线（代价 `3√2 ≈ 4.243`）换成 `4` 步直线（代价 `4`）—— 多一步，反而短了 0.243。
有障碍强迫你在"斜着挤过去"和"绕个直角"之间选择时，这种局面完全会出现。

（顺带说明：在**没有障碍**的 8 邻域空地上两者恰好一致，因为最优路正好是
`max(dx,dy)` 步 —— 既最少步数、又最短距离。所以在空地上测不出 BFS 的毛病，
这也是这类 bug 容易溜过去的原因。）

再往前一步：一旦边代价不只是 1 和 √2 —— 比如加上地形代价，草地 2、公路 1 ——
BFS 就彻底没救了。Dijkstra 对任何非负边权都成立。

## 1.3 Dijkstra 的核心思想：贪心 + "已定"集合

Dijkstra 维护两个东西：

- `g[v]`：目前**已知**的从起点到 `v` 的最短代价。初值 `+∞`，`g[s] = 0`。它是"事实"，会被不断改小。
- 两个集合：
  - **CLOSED**（已定）：`g` 已经确定是最短，永远不再改；
  - **OPEN**（待定）：已经被发现（`g < +∞`），但还不能确定最短。

一轮循环干两件事：

```
1. 从 OPEN 里挑 g 最小的点 cur，把它移进 CLOSED   <- 贪心的那一步
2. 对 cur 的每个邻居 nb 做"松弛(relax)"：
      if g[cur] + c(cur,nb) < g[nb]:
          g[nb] = g[cur] + c(cur,nb)
          parent[nb] = cur
          把 nb 放进/更新到 OPEN
```

"松弛"这个词的意思是：`g[nb]` 原本是个上界（"我知道有条路要花这么多"），
现在发现了更便宜的走法，就把这个上界**放松**下来。

整个算法就是不停地松弛，直到没有待定的点。

### 关键洞察：为什么"挑 g 最小的"就能定下来

这是 Dijkstra 唯一需要证明的地方，也是唯一值得想明白的地方。

**命题**：从 OPEN 中取出 `g` 最小的点 `cur` 时，`g[cur]` 已经是真实最短代价了。

**证明**（反证）：假设还存在一条更短的路 `P: s → … → cur`，代价 `< g[cur]`。

沿着 `P` 从 `s` 往 `cur` 走，`s` 在 CLOSED 里（第一步就进去了），`cur` 不在。
所以 `P` 上必然存在**第一个不在 CLOSED 里的点** `z`（可能 `z = cur`）。
`z` 的前一个点 `y` 在 CLOSED 里，而 `y` 进 CLOSED 时松弛过它的所有邻居，
包括 `z` —— 所以 `z` 一定已经在 OPEN 里，且

```
g[z] ≤ g[y] + c(y,z) = P 上 s→z 这一段的代价
```

又因为**边权非负**，`P` 上 `z→cur` 那一段代价 ≥ 0，于是

```
g[z] ≤ (P 上 s→z 的代价) ≤ (整条 P 的代价) < g[cur]
```

得到 `g[z] < g[cur]`，而 `z` 和 `cur` 都在 OPEN 里 —— 这和"`cur` 是 OPEN 里 `g` 最小的"矛盾。∎

请注意证明里**唯一**用到的额外假设：**边权非负**。这不是可有可无的技术细节，
它就是 Dijkstra 的命门，见下一节。

推论：**CLOSED 里的点可以放心地永不回头**。这直接给出了伪代码第 7 行
（`nb 在 CLOSED 就跳过`）的合法性 —— 见 `astar.cpp` 的 `[伪代码 4]` 和 `[伪代码 7]`。

## 1.4 负权为什么让 Dijkstra 崩掉

上面的证明在 `c ≥ 0` 处断掉，那就一定能构造反例：

```
        s --(1)--> A --(-5)--> B
         \
          --(2)--> B
```

Dijkstra 的过程：

1. `s` 出堆，松弛得到 `g[A] = 1`、`g[B] = 2`；
2. OPEN 里 `A(1)` 比 `B(2)` 小，`A` 出堆并进 CLOSED，松弛得到 `g[B] = 1 + (-5) = -4`；
3. `B` 出堆，`g[B] = -4`。

这次侥幸对了。把数字改一下：

```
        s --(3)--> A --(-5)--> B
         \
          --(2)--> B
```

1. `s` 出堆，`g[A] = 3`、`g[B] = 2`；
2. OPEN 里 `B(2)` 最小，**`B` 先出堆进 CLOSED，`g[B]` 被钉死在 2**；
3. `A` 出堆，松弛发现 `3 + (-5) = -2 < 2` —— 但 `B` 已经在 CLOSED 里，按规则跳过。

结果 `g[B] = 2`，真实答案是 `-2`。**错了**。

负权要用 Bellman-Ford（O(VE)，允许反复松弛）。栅格地图上代价是几何距离，
天然非负，所以不用操心 —— 但如果哪天你把"下坡省电"建模成负代价，这个坑就在等着你。

## 1.5 OPEN 用什么数据结构

每轮要"取出 `g` 最小的"，这就是优先队列的活儿。但有个麻烦：松弛会**改小**已在队列里的
节点的 `g`，标准二叉堆不支持"改键"（decrease-key）。三种应对：

| 方案                    | 做法                                                                                            | 复杂度             | 谁在用                                          |
| ----------------------- | ----------------------------------------------------------------------------------------------- | ------------------ | ----------------------------------------------- |
| **懒惰删除**      | 不改旧条目，直接再 push 一条新的`(g, id)`；出堆时发现节点已 CLOSED 或条目已过期，就当垃圾丢掉 | `O((V+E) log E)` | 本包（`std::priority_queue`）                 |
| `multimap` + 存迭代器 | 更新时`erase` 旧的、`insert` 新的                                                           | `O((V+E) log V)` | 作业的`grid_path_searcher/graph_searcher.cpp` |
| 斐波那契堆              | 真正的 O(1) 均摊 decrease-key                                                                   | `O(V log V + E)` | 教科书里，实际几乎没人用（常数太大）            |

懒惰删除的开销是可以量化的 —— `SearchStats::stale_pops` 就是被丢掉的过期条目数。
在这个包的实测里它很小（`tiny` 地图 30 次入堆里只有 1 次过期），
换来的是代码短得多、也不需要维护"节点→堆位置"的映射。

本包的实现见 `astar.h` 里的 `AStar::OpenList` / `QueueGreater`，
丢弃过期条目的那两行在 `astar.cpp` 的 `[伪代码 3]` 附近。

## 1.6 复杂度

用二叉堆：**`O((V + E) log V)`**。栅格地图上 `E ≤ 8V`，所以就是 `O(V log V)`。

`V` 是**格子数**，随分辨率的平方增长 —— 这是栅格法的根本代价：
把分辨率提高一倍，格子数变 4 倍。这也是后面所有优化（A*、JPS、分层规划）
真正想解决的问题。

## 1.7 亲手跑一遍

21×11 空地图，起点 `(1,5)`，终点 `(19,5)`：

```bash
rosrun astar_tutorial astar_console_demo \
    --map empty --size 21 11 --h zero --start 1 5 --goal 19 5 --range 99999 99999
```

最终状态（`x` = CLOSED，`o` = OPEN，`*` = 最终路径）：

```
x x x x x x x x x x x x x x x x x o o . .
x x x x x x x x x x x x x x x x x x o . .
x x x x x x x x x x x x x x x x x x o o .
x x x x x x x x x x x x x x x x x x x o .
x x x x x x x x x x x x x x x x x x x o .
x S * * * * * * * * * * * * * * * * * G .
x x x x x x x x x x x x x x x x x x x o .
x x x x x x x x x x x x x x x x x x x o .
x x x x x x x x x x x x x x x x x x o o .
x x x x x x x x x x x x x x x x x x o . .
x x x x x x x x x x x x x x x x x o o . .

扩展节点数 : 202   (地图共 231 格)
路径代价   : 18.0000 格
```

**231 格里扩展了 202 格**，只为了走一条 18 格的直线。

路径是最优的，一点问题没有。但注意左边那一大片 `x`：Dijkstra 往**远离终点的方向**
也铺了同样多的格子。它必须这么做 —— 因为它压根不知道终点在哪儿。

这就是下一篇要解决的浪费。

想单步看清每一格是怎么定下来的，用一个手算规模的地图（5×3、4 邻域）：

```bash
rosrun astar_tutorial astar_console_demo \
    --map empty --size 5 3 --conn 4 --h zero --start 0 1 --goal 4 1 --step --no-skips
```

它出堆的顺序是 `g = 0, 1, 1, 1, 2, 2, 2, 3, 3, 3, 4, 4` —— **严格不减**。
这不是巧合，正是 1.3 那个证明的直接推论：出堆的 `g` 序列一定单调不减。
如果你自己写的 Dijkstra 出现了"后出堆的 g 反而更小"，那必定有 bug。
